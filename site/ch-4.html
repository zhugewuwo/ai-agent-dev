第2.5章：用 AI 接管工程化开发：从工程底座到能力链路

本章为过渡章节的补充更新。由于部分代码开发进度存在不一致的地方，导致章节中的示例内容略显割裂，因此本次对相关内容进行补充和衔接优化。 感谢大家的理解与支持。如有问题，欢迎在评论区留言，或添加我的微信一起交流讨论。

第二章里，我们已经把智能体工程的底座搭了起来：monorepo、Web、API、共享包、Compose，以及一套可以被 AI 代理复现的工程初始化流程。第三章会正式进入 LangChain，把“调用一次模型”逐步整理成可维护、可测试的服务端能力链路。

本章分支feat/user-system

在这两章之间，最好不要直接跳过去。因为真实开发里还有一个很容易被忽略的问题：当工程底座已经有了，AI 到底应该怎样参与后续开发，才不会把项目带偏？

这一章先停在中间地带：不重复第二章的工程搭建细节，也不提前展开第三章的 LangChain API，而是把 Superpowers、ui-ux-pro-max 和一个 RBAC 用户权限系统放在一起，看看 AI 编程怎样从“能生成代码”走向“能按工程节奏交付”。

后文仍然会围绕一个具体案例展开：单租户后台管理系统里的 RBAC 用户权限系统。这个案例会碰到后端建模、接口、鉴权、前端页面、联调与交付，但又不会把 ABAC、行级权限、组织继承、多租户隔离这些更重的主题一起拖进来。

这是最终完成初版的多系统 RBAC 用户系统项目，仓库地址为 https://github.com/Cookieboty/Autix。需要注意的是，这个项目虽然是按下文流程推进出来的，但过程中依然做了不少 bug 处理；受 AI 幻觉影响，部分分支也出现过偏差。正因如此，本章更想强调的不是“AI 一次生成完整系统”，而是怎样让 AI 在可控流程里持续推进真实项目。

一、Superpowers 与 ui-ux-pro-max 的定位

1.1 Superpowers：面向工程流程的 AI 开发工作流

很多 AI 编程体验之所以让人又爱又烦，本质上不是模型不会写代码，而是它太容易过早进入实现阶段。你刚抛出一个需求，它就开始生成文件；你话还没说完，它已经默认做了三层扩展。

Superpowers 的核心思路，正是把这种“先写再说”的节奏，改造成一套更接近工程实践的工作流。它并不是单一 Skill，而是一套围绕软件开发流程组织起来的技能系统：从 brainstorm、plan，到执行、TDD、review、收尾，尽量让代理在每个阶段做该做的事。

1.2 ui-ux-pro-max：面向前端产出的设计增强能力

很多人第一次用 AI 生成前端页面时，都会有一种熟悉的感觉：布局也有，按钮也有，表格也有，生了一堆组件；但页面往往停留在“摆上去”的层面，缺少真正的设计判断——比如配色节奏、版式层级、字号体系、交互一致性。

ui-ux-pro-max 官方 README 对它的定位，是一个为多平台 AI coding assistant 提供 design intelligence 的 Skill。它不是一个 UI 组件库，也不是设计工具，而更像一个给模型补设计经验的知识层。

1.3 两者的互补关系

  • Superpowers：解决“开发过程是否可控”
  • ui-ux-pro-max：解决“前端结果是否足够成熟”

1.4 何时使用 Superpowers，何时使用 ui-ux-pro-max

Superpowers 适合的场景：

  • 中大型功能开发，一次对话内完成不了
  • 任务同时涉及后端建模、接口、前端、测试的多模块联动
  • 需要跨 session 持续推进，上下文断了也要接着恢复
  • 需要可审计、可复盘的交付结果

不容易起效的场景：

  • 修一个很小的 bug、一次性脚本、快速验证原型的任务
  • 尚在探索方向、需求本身就不收敛的创意型工作

ui-ux-pro-max 适合的场景：

  • 页面目标和组件库已经确定，你需要的是更统一、更成熟的设计产出
  • 技术栈比较主流（React、Next.js、Tailwind 等）
  • 不适合：尚在探索风格方向、仓库本身设计不统一或项目组件混乱的情况

💡 实践中最常见的用法：先用 Superpowers 把任务拆清楚、推到后端骨架就位，再用 ui-ux-pro-max 进入前端阶段。两个工具的切换点是自然的：前者管流程，后者管前端界面。

三、官方工作流概览

按照官方 README，Superpowers 的基本工作流如下：

  1. brainstorming
  2. using-git-worktrees
  3. writing-plans
  4. subagent-driven-development 或 executing-plans
  5. test-driven-development
  6. requesting-code-review / review 相关环节
  7. finishing-a-development-branch

3.1 需求澄清

对应 brainstorming。它不是“礼貌地追问几句”，而是把模糊需求转成一个能继续往下推的设计起点。最关键的产物不是聊天记录，而是后续会被固化下来的设计判断。

3.2 方案收敛与计划拆分

对应 writing-plans。AI 应把任务拆成一组可以逐步完成、逐步验收的动作。官方文档里一直强调 plan 的粒度要小，就是为了让长任务不会因为上下文膨胀而失控。

3.3 执行阶段的约束机制

对应 executing-plans、subagent-driven-development 和 test-driven-development。Superpowers 想做的是，让执行阶段继续受到测试、review 和阶段性检查的约束，而不是有了计划也照样一口气往前冲。

3.4 收尾与交付

对应 finishing-a-development-branch。很多 AI 生成代码的问题，不在生成时，而在收尾时：没确认测试结果，没做回归，也没有明确说明当前分支该如何处置。

3.5 ui-ux-pro-max 的工作方式

你提出任何 UI/UX 相关任务，Skill 在相关平台上自动激活，然后识别任务类型，检索对应的风格、配色、字体、布局建议，再把这些结果提供给模型。它更像“设计顾问”，而不是“页面生成器”。

四、RBAC 案例的选择

RBAC 系统之所以合适作为演示案例，是因为它天然有几层结构：后端要建模用户、角色、权限；接口层要做 Guard 和装饰器；前端要做登录、列表、权限分配、菜单控制；交付阶段还要处理联调、初始化数据和容器化启动。这正好能把 Superpowers 的长任务工作流和 ui-ux-pro-max 的前端辅助能力放进同一个案例里观察。

📌范围边界：本文讨论的是单租户后台管理系统里的 RBAC，不涉及 ABAC、数据行级权限、组织/部门继承、多租户隔离等更复杂的权限模型。

五、在 RBAC 项目中的使用方式

5.1 需求边界澄清

权限系统最容易出问题的，不是 CRUD 本身，而是边界不清时默认做了太多假设。所以第一步不是写代码，而是让 AI 先把问题问完整。

  • 🤖 Prompt：需求边界澄清

    /superpowers:brainstorm

我要做一个后台管理系统的 RBAC 权限模块。
后端使用 NestJS + Prisma + PostgreSQL，前端使用 Next.js 16 + Tailwind 4 + HeroUI。

请不要直接写代码，先帮我把边界条件问清楚，包括：
- 权限粒度到页面、按钮还是接口
- 是否需要 super_admin 绕过机制
- refreshToken 是否落库
- 是否需要审计日志
- 是否涉及组织 / 部门 / 租户维度

这一步的意义非常大。你以为自己要的是“后台权限控制”，模型理解成了“完整企业权限平台”；你只想做按钮级控制，它顺手给你加上了租户维度和审计模型。超出范围的内容局部不一定错，但大概率不是你当下真正需要的东西。

5.2 Spec 设计说明

一旦问题问得差不多了，让 AI 把核心决策收敛成一份设计说明。有没有把下面几件事说死才是关键：

  • 后端模块怎么拆
  • 权限命名采用什么规范
  • 前端如何接入权限判断
  • 哪些内容这次明确不做

如果这些东西不先落下来，后面生成的 Plan 再细，也只是把一堆摇摆中的决定拆得更碎而已。

5.3 Plan 拆分原则

不要用“实现用户模块”这种粗粒度的任务名。一步里面包含的决策越多，执行时越容易发散。

后端验收清单：

本项目里用户系统服务（@autix/user-system）监听 4002 端口，并通过 setGlobalPrefix('api') 统一加 /api 前缀；登录用用户名而非邮箱。种子账号见 packages/database/prisma/seed.ts（超管 admin / Admin@123456）。

# 登录获取 Token（用户名 + 密码）
curl -X POST http://localhost:4002/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"Admin@123456"}'

# 获取用户信息，携带 Token 应返回 200
curl -X GET http://localhost:4002/api/auth/profile \
    -H "Authorization: Bearer$ACCESS_TOKEN"

# 无权限的 Token 删除用户应返回 403（不是 401）
curl -X DELETE http://localhost:4002/api/users/<userId> \
  -H "Authorization: Bearer <limitedToken>"

# super_admin 应能访问所有接口
curl http://localhost:4002/api/users \
  -H "Authorization: Bearer <superAdminToken>"

前端权限控制实现示例：

// store/auth.store.ts
const hasPermission = (permission: string) => {
  if (!user) return false;
  if (user.isSuperAdmin) return true;

  const permissions = Array.isArray(user.permissions)
    ? user.permissions.map((p) => typeof p === 'string' ? p : p.code)
    : [];

  return permissions.includes(permission);
};

// 按钮级权限控制
{ hasPermission('user:delete') && (
  <Button variant="ghost" onClick={() => setDeleteConfirmUser(userItem)}>
    删除用户
  </Button>
)}

// 菜单级权限控制
const visibleMenus = menus.filter((menu) => menu.visible && !menu.parentId);

最终验收标准：

  • ✅ services/user-system 和 clients/admin-web 本地服务正常启动
  • ✅ 初始化脚本正常写入权限和管理员账号
  • ✅ 前端登录后 Token 注入正常，接口可访问
  • ✅ 401 自动刷新或跳转登录页
  • ✅ 配置项集中在环境变量和包脚本中

六、适用场景与现实限制

6.1 真正适合它的场景

  • 中大型功能开发：不是几个小修小补，而是会牵涉模型、接口、页面、测试的完整模块
  • 多模块联动任务：前后端、交互、鉴权、配置、联调需要协同推进
  • 需要跨 session 续做的任务：一次对话干不完，后面还要继续接着做
  • 需要复盘与审计的交付：你希望知道设计是怎么定的、每一步做到哪了、为什么这样做

6.2 不适合全流程的场景

  • 修一个很小的 bug
  • 一次性脚本
  • 快速验证想法的原型
  • 本来就需要边做边改方向的创意型任务

一句话说就是：小任务轻流程，大任务重流程。

6.3 现实限制

Spec / Plan 确实会带来前置成本

如果任务本来就很小，前面花十几分钟对齐、落文档、拈计划，可能真的不划算。

TDD 会让 AI 显得更慢

它的好处是结果更可验证，但代价就是执行节奏不会像“直接写一版能跑的代码”那么快。

ui-ux-pro-max 的效果依赖代码基线

如果你的仓库本身组件体系混乱、设计 token 失控、页面结构脏乱，那它的上限也会被拉低。

人工决策依旧不可替代

Skill 能加强执行，但不能替你决定：哪些复杂度该引入、哪些边界这次先不做、什么时候追求速度还是追求稳定。

七、小结：把 AI 放回工程节奏里

第 2 章已经把路铺好：Web、API、共享包、Compose 都能跑起来，代理也有了一份可以照着复现的工程说明。

但工程底座只是起点。真正进入功能开发时，问题会变成另一种形态：需求边界会摇摆，后端和前端会互相影响，权限模型稍微多想一步就会膨胀，页面看起来能用却不一定像一个成熟后台。

所以这一章没有继续堆代码，而是先把开发节奏讲清楚。

RBAC 这个例子里，比较关键的不是“AI 生成了多少文件”，而是几件事有没有被稳住：

  • 需求边界先收窄，别让模型顺手加出一套企业级权限平台；
  • Spec 先把核心决策写死，后面的 Plan 才不会拆得越细越偏；
  • 后端先跑通可验证骨架，接口、权限、初始化数据和 curl 验收都要落地；
  • 前端等页面目标和接口形态明确后再打磨，否则设计增强也只是给不稳定的需求套皮；
  • 集成阶段单独处理，Token 注入、401/403、启动脚本和种子数据都不能留到最后“顺手补一下”。

这也是它放在第 2 章和第 3 章之间的原因：第 2 章讲工程结构，第 3 章讲模型能力如何进入服务端；而这一章夹在中间，讲的是在真正把模型能力接进系统之前，先把 AI 辅助开发这件事变得可控。

第二章解决“工程怎么搭起来”，这一章解决“AI 怎么参与开发”，第三章再开始解决“模型能力怎么进入系统”。

八、延伸：跑完整流程时要关注模型成本

用 Superpowers 推进大任务、用 ui-ux-pro-max 打磨前端，本质上都是在让模型做更多事。做得越多，Token 消耗越真实，模型选型的代价也越具体。

当一个任务从 brainstorm、Spec、Plan、执行、review 一路走到集成交付时，几个问题会变得很实际：

  • 哪些阶段必须用强模型，哪些阶段可以切换到更便宜的小模型？
  • 缓存命中率到底有多少？Prompt 前缀是否足够稳定？
  • 每一步的输入、输出、缓存 Token 分别是多少？
  • 优化上下文之后，成本到底降低了多少？

这些问题后面还会反复出现。Agent 工程不只是“能不能生成”，还包括“能不能长期、稳定、可控地运行”。

如果你已经在使用统一模型接入层，例如 Amux API 或类似平台，可以把它当作实验环境，观察不同模型、不同 Prompt 和不同上下文策略下的成本变化。

倍率只是起点。真正决定它是否适合工程场景的，通常是充值口径、缓存表现、计费透明度、稳定性和模型切换成本。

九、下一章

到这里，过渡就完成了。

下一章正式进入 LangChain：不再讨论“怎样让 AI 帮我们写代码”，而是把模型调用本身接进 Nest 服务端，并逐步整理成一条可维护、可测试、可复用的能力链路。

从这里开始，关注点会从开发流程切到系统能力：

  • 这一章：AI 怎么更稳地参与开发；
  • 下一章：AI 能力怎么真正进入服务端。

只有先把工程结构和开发节奏稳住，后面接入模型、提示模板、结构化输出、工具调用和 Agent Runtime 时，复杂度才有地方安放。
