面试篇：Agent 基础与编排

本篇先解决 Agent 面试里最基础、也最容易被问穿的问题：Agent 到底是什么、它和 Chatbot / Workflow 有什么区别、为什么需要 LangGraph、多 Agent 什么时候才有必要。这里的重点不是背概念，而是建立一套工程判断框架。

1. 什么是 AI Agent？它和普通 Chatbot 有什么区别？

问题

什么是 AI Agent？它和普通 LLM 聊天机器人有什么本质区别？

回答

AI Agent 不是简单的「会聊天的模型」，而是一个围绕目标持续推进任务的工程系统。它通常具备理解目标、维护状态、规划步骤、调用工具、观察结果、修正行动并交付结果的能力。

普通 Chatbot 更像是：

用户输入 → 模型生成回答 → 对话结束

Agent 更像是：

用户目标
→ 判断任务类型
→ 拆解步骤
→ 查询知识 / 调用工具
→ 观察结果
→ 修正计划
→ 生成可交付结果

所以二者的关键区别不是「是否用了大模型」，而是系统是否具备持续行动能力。

Chatbot 主要解决「回答问题」，Agent 更偏向「完成任务」。例如用户问「OAuth2 授权码模式是什么」，普通 Chatbot 可以解释概念；但如果用户说「帮我评估企业微信登录方案，并给出安全风险和验收标准」，Agent 就需要结合知识库、业务上下文、安全规则和结构化输出，形成一份可用报告。

解读

只回答下面这句会显得过窄：

Agent = LLM + Tools

更合适的展开方式，是从行为能力和工程约束两个角度说明：

  • 是否能维护任务状态
  • 是否能自主决定下一步
  • 是否能调用外部工具
  • 是否能根据观察结果调整
  • 是否能输出可交付产物
  • 是否有权限、成本、观测和评估约束

真正的工程区别在于：Agent 一旦能调用工具，就会产生副作用、消耗资源、影响真实系统。因此，Agent 不是一个 Prompt 技巧，而是一个需要被治理的执行主体。

2. Agent 的核心组成部分有哪些？

问题

一个完整的 Agent 系统通常由哪些核心模块组成？

回答

一个工程化 Agent 系统通常包括：

1. 什么是 AI Agent？它和普通 Chatbot 有什么区别？

  1. Model
    • 提供语言理解、推理、生成和工具选择能力。
  2. Instruction / Prompt
    • 定义角色、目标、约束、输出格式和安全边界。
  3. State / Memory
    • 保存对话历史、任务状态、中间产物和长期上下文。
  4. Tools
    • 连接搜索、数据库、代码执行器、业务 API、MCP server 等外部能力。
  5. Planner / Router
    • 判断任务走哪条路径，是直接回答、RAG、工具调用、多 Agent，还是长任务编排。
  6. Executor
    • 执行具体步骤，包括模型调用、工具调用、子任务调度和结果汇总。
  7. Evaluator / Critic
    • 对输出做质量检查、反思、打分、结构校验或触发重试。
  8. Guardrails
    • 输入校验、Prompt Injection 防护、工具白名单、权限控制、预算限制。
  9. Observability - 记录日志、trace、token usage、工具调用、错误率、延迟和成本。

解读

这题的重点，是把 Agent 放在工程系统里理解。

只列基础三件套通常不够：

Agent = LLM + Memory + Tools

还需要补上：

Agent 还需要路由、状态、评估、安全、观测、权限和成本控制。

生产环境中，Evaluator、Guardrails、Observability 往往比「多接几个工具」更重要。因为真正出问题时，通常不是模型不会回答，而是：

  • 工具调错了
  • 权限越界了
  • 检索内容没被消费
  • 成本突然上涨
  • 长任务无法恢复
  • 输出质量没有评估
  • 出错后没人知道原因

3. Agent 和 Workflow 的区别是什么？

问题

AI Agent 和传统 Workflow / Pipeline 有什么区别？什么时候该用 Agent，什么时候该用 Workflow？

回答

Workflow 是预先定义好的流程，执行路径在开发阶段基本确定。例如：

输入需求 → 提取字段 → 风险分析 → 生成报告

Agent 更强调运行时决策。它可以根据当前状态判断：

  • 是否需要补充信息
  • 是否需要调用搜索
  • 是否需要进入工具调用
  • 是否要拆成多个子任务
  • 是否要交给某个专家 Agent
  • 是否需要反思或重试

可以这样对比：

维度 Workflow Agent
执行路径 开发时固定 运行时动态决定
可控性 高 相对低
灵活性 中等 高
成本 可预测 更难预测
适用场景 标准流程、稳定任务 开放式、多步、不确定任务

如果任务路径稳定、规则明确，优先使用 Workflow；如果任务开放、步骤不确定、需要动态调用工具，再考虑 Agent。

解读

这题的重点是能否克制使用 Agent。

不能简单认为「Agent 比 Workflow 更高级」。真实工程里，很多稳定流程用 Workflow 更好，因为它：

  • 更便宜
  • 更快
  • 更可测试
  • 更容易控制
  • 更容易解释和回滚

更合理的方案通常是 Workflow + Agent 混合架构：

外层 Workflow 控制主流程
→ 局部复杂节点交给 Agent
→ 关键动作由规则、权限和审批兜底

例如需求分析系统可以用固定图控制主流程，但在「多专家分析」「工具选择」「长任务规划」等局部使用 Agent。

4. ReAct、Plan-and-Execute、Reflexion 分别是什么？

问题

请解释 ReAct、Plan-and-Execute、Reflexion 三种 Agent 推理模式。

回答

ReAct 是 Reasoning + Acting，即「边思考、边行动」。Agent 每轮先推理，再选择工具，再观察结果，再继续下一轮。

Thought → Action → Observation → Thought → Action → Observation → Final

它适合搜索、工具调用、交互式探索等场景。

Plan-and-Execute 是先规划再执行。Agent 先把任务拆成多个步骤，然后逐步执行，必要时重新规划。

制定计划 → 执行步骤 1 → 执行步骤 2 → 汇总结果

它适合长任务、跨系统任务、代码修改、调研报告等场景。

Reflexion 是反思机制。Agent 执行后对结果进行自我评估，发现遗漏、错误或冲突后修正策略。

执行 → 评估 → 反思 → 改进 → 再执行

它适合质量提升、报告润色、错误修正和评审型任务。

解读

面试中容易把这三者说成互斥方案。更准确的理解是：它们属于不同层面。

  • ReAct 偏执行层
  • Plan-and-Execute 偏规划层
  • Reflexion 偏优化层

真实系统通常组合使用。例如：

先 Plan 拆任务
→ 每个步骤用 ReAct 调工具
→ 最后用 Critic / Reflexion 检查质量

但要注意，反思和循环不能无限执行，必须设置最大迭代次数、最大 token、最大工具调用次数和超时。

5. LangChain 主要解决什么问题？

问题

LangChain 在 Agent 应用开发中主要解决什么问题？

回答

LangChain 主要解决 LLM 应用开发中的能力组合问题。它提供了一组抽象，用来连接：

  • 模型调用
  • Prompt 模板
  • 输出解析
  • Memory
  • Tools
  • Retriever
  • Runnable 链式组合
  • Agent 执行器

它让开发者可以把一次模型调用扩展成一条可组合的能力链路。

例如：

PromptTemplate → ChatModel → OutputParser

进一步可以变成：

History → Retriever → Prompt → Model → Parser → Tool

解读

不要把 LangChain 说成 Agent 本身。它更像 LLM 应用的基础组件库。

现代 LangChain 的核心是 LCEL（LangChain Expression Language）：用 | 把 Prompt、Model、Parser、Retriever 等 Runnable 组合成链，天然支持流式、批处理和异步。

什么时候不该用 LangChain 也要能说清楚：

  • 只是单次调用模型：直接用厂商 SDK 更轻。
  • 追求极致可控和最小依赖：可以用原生 function calling 自研薄封装。
  • 需要复杂状态、路由和循环：应该上 LangGraph，而不是用 LangChain 硬拼。

反过来，当系统开始需要 Prompt 管理、RAG、工具调用、结构化输出、Memory 和链式组合时，LangChain 的价值才会真正体现。

6. LangGraph 和 LangChain 的关系是什么？

问题

LangGraph 和 LangChain 是什么关系？为什么有了 LangChain 还需要 LangGraph？

回答

LangChain 提供模型、工具、Prompt、Retriever、Runnable 等基础组件；LangGraph 在这些组件之上提供状态机和图运行时。

LangChain 更像能力组件库，LangGraph 更像可控的 Agent 编排运行时。

LangGraph 适合处理：

  • 多节点流程
  • 条件路由
  • 循环执行
  • 多 Agent 协作
  • 状态合并
  • Checkpoint
  • Human-in-the-loop
  • 流式事件

例如需求分析 Agent 可以设计成：

triage → extract → clarify → experts → critic → summary

每个节点可以是模型调用、工具调用、规则判断或子 Agent。图负责控制状态流转和执行路径。

解读

这题的重点，是区分组件调用和流程编排。

回答时可以抓住四点：

  • LangChain 解决组件化
  • LangGraph 解决状态化和流程控制
  • 复杂 Agent 不应该只靠顺序链式调用或 if/else 硬编码拼接
  • 图结构更利于测试、观测、恢复和扩展

7. LangGraph 中 State 的作用是什么？

问题

LangGraph 为什么需要 State？State 在 Agent 系统里承担什么作用？

回答

State 是图执行过程中的共享上下文和状态容器。它记录节点之间传递的数据。

典型 State 可能包括：

  • 用户输入
  • 对话历史
  • 当前意图
  • 结构化需求
  • 检索上下文
  • 专家分析结果
  • 风险判断
  • 最终报告
  • 错误信息
  • 消息列表

State 的作用是让节点之间通过明确的数据结构通信，而不是依赖隐式变量或临时拼接。

解读

Agent 系统复杂后，最大问题之一是中间状态不可见。State 可以让系统更可控：

  • 更容易测试每个节点
  • 更容易追踪执行过程
  • 更容易恢复任务
  • 更容易做 checkpoint
  • 更容易验证上游结果是否被下游消费

例如 RAG 检索结果如果只是查出来但没有写入 State，后面的 summary 节点就无法真正使用它。

8. Router Node 的作用是什么？

问题

Router Node 的作用是什么？为什么不直接让所有节点顺序执行？

回答

Router Node 用来根据当前输入和状态决定下一步走哪条路径。

例如：

  • 普通问答 → 直接回答
  • 需求分析 → 进入分析图
  • 多工单任务 → 进入 DeepAgent
  • 敏感输入 → 进入安全拒答或人工审批
  • 信息不足 → 进入澄清节点

如果所有节点都顺序执行，会带来几个问题：

  • 简单问题被复杂化
  • 不必要的模型调用增加成本
  • 延迟变高
  • 输出质量被无关步骤干扰
  • 安全分支难以控制

解读

Router Node 本质上是 Agent 系统的控制面。它决定任务交给谁处理、走多深、是否需要工具、是否需要人工介入。

生产系统里，路由最好遵循：

能用规则确定的，不要强行用 LLM；需要语义判断的，再交给 LLM。

例如输入包含多个 REQ 编号触发长链路由，就可以用确定性规则完成，低成本、低延迟、可测试。

9. Multi-Agent 适合解决什么问题？

问题

什么情况下适合使用 Multi-Agent？是不是 Agent 越多越好？

回答

Multi-Agent 适合任务天然需要多个角色、多个视角或多个专业能力协作的场景。

例如需求分析中可以拆成：

  • 功能专家：分析业务流程和功能边界
  • 技术专家：分析架构、接口、数据模型
  • 安全专家：分析权限、隐私、攻击面
  • 风险专家：分析依赖、成本、上线风险
  • 总结 Agent：汇总多方观点形成报告

但 Agent 不是越多越好。Agent 越多，系统会面临：

  • token 成本上升
  • 延迟变长
  • 输出冲突增加
  • 状态合并复杂
  • 调试难度上升
  • 评估成本增加

解读

一个 Prompt 能稳定解决的问题，不需要 Multi-Agent。只有当任务确实需要多角色、多视角、多阶段协作时，才值得引入。

控制复杂度的方式包括：

  • 使用 Supervisor 或 Router 管理分工
  • 给每个 Agent 明确职责和输入输出
  • 用结构化 State 合并结果
  • 用 Critic 检查冲突
  • 用评估集验证收益是否超过成本

10. Multi-Agent 有哪些协作拓扑？Agent 之间如何通信？

问题

Multi-Agent 常见的协作结构有哪些？多个 Agent 之间如何传递信息？

回答

常见拓扑可以分为几类：

  1. Supervisor（主管式）
    • 一个 Supervisor 负责分发任务给子 Agent，并汇总结果。
    • 优点是分工清晰、易于控制和审计；缺点是 Supervisor 容易成为瓶颈。
  2. Network / Peer（网状 / 对等）
    • Agent 之间可以互相调用或移交控制权。
    • 灵活但难控制，容易出现环路和职责重叠。
  3. Hierarchy（分层）
    • Supervisor 下面还有子 Supervisor，适合超大任务分治。
  4. Sequential / Pipeline（顺序）
    • Agent 按固定顺序接力，更接近 Workflow。

Agent 之间的通信方式主要有三种：

  • 共享 State：所有 Agent 读写同一个状态对象，适合 LangGraph 这类图运行时。
  • 消息传递：Agent 之间显式发消息，类似 actor 模型。
  • Handoff（移交）：当前 Agent 把控制权和上下文直接交给另一个 Agent。

例如一个代码审查系统可以用 Supervisor 拓扑：Supervisor 把 PR 分给「风格检查 Agent」「安全审计 Agent」「测试覆盖 Agent」，各自把结论写入共享 State，最后由 Supervisor 汇总成审查意见。

解读

这题的重点，是区分「多角色提示词」和「可控协作系统」。

选拓扑的核心判断是：

能用 Supervisor 集中控制的，就不要用 Network 放任互相调用。

生产系统里 Supervisor / Hierarchy 更常见，因为它们可控、可观测、可审计。Network 虽然灵活，但环路、职责重叠和状态冲突会让调试成本急剧上升。通信方式上，共享 State 最容易追踪和恢复；Handoff 要特别注意上下文裁剪，否则会把无关历史一起带过去。

11. 主流 Agent 框架如何选型？

问题

除了 LangChain / LangGraph，还有哪些常见 Agent 框架？如何选型？

回答

常见框架大致可以分为几类：

框架 定位 适合场景
LangGraph 基于图的状态机编排 需要显式状态、路由、循环、checkpoint 的复杂流程
AutoGen 多 Agent 对话式协作 多 Agent 讨论、代码执行、研究型任务
CrewAI 角色 + 任务的高层抽象 快速搭建角色分工明确的多 Agent
OpenAI Agents SDK 轻量 Agent + handoff + guardrails 以 OpenAI 模型为主、想要简单编排

选型时可以从几个角度判断：

  • 是否需要显式状态和可恢复执行（偏向 LangGraph）
  • 是否以多 Agent 对话为核心（偏向 AutoGen）
  • 是否追求快速搭建和高层抽象（偏向 CrewAI）
  • 是否绑定单一模型厂商、想要最小依赖（偏向厂商官方 SDK）

解读

不必陷入「哪个框架最好」的争论。更实用的判断是：

框架只是编排层，关键看任务对状态、可控性、可观测性和可恢复性的要求。

很多团队的真实选择是：底层用 LangGraph 控制状态和流程，局部复杂协作再引入更高层的多 Agent 抽象。也有团队在需求稳定后干脆用原生 function calling + 自研编排，去掉框架依赖以降低不确定性。

本篇小结

这一篇的核心是建立 Agent 的基础判断框架。

面试中最稳的表达方式是：

  1. 简单任务优先 Workflow；
  2. 动态决策才引入 Agent；
  3. 多角色复杂任务才引入 Multi-Agent；
  4. 复杂流程用 LangGraph 管理状态和路由；
  5. 一切自主性都必须被状态、权限、成本和评估机制约束。

可以收束为：

Agent 不是更复杂的 Chatbot，而是一个会调用工具、维护状态、消耗资源、影响外部系统的工程实体。LangGraph 和 Multi-Agent 的价值，不是炫技，而是让复杂任务可控、可测、可观测、可恢复。
